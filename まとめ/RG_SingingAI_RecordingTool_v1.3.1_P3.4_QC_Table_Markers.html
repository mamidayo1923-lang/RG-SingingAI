1. プロジェクト概要

1.1 RG Singing AI の目的

RG Singing AI は、人間の歌声を分析し、歌声の音響的な特徴や歌唱表現を学習することを目指すプロジェクトである。

最終的には、単に MIDI の音程に従って音を出すだけではなく、実際の歌唱に含まれる次のような特徴を扱えるシステムを目指す。

  • 音高と音高変化
  • 音量と音量変化
  • 母音・子音などの音素に関する情報
  • 声道による音色の変化
  • 声の息漏れや息の混ざり方
  • 声帯振動の周期性
  • ビブラート
  • 音の立ち上がりと収束
  • 音程の移行やポルタメント
  • 発声の強さや柔らかさ
  • 音素と音符の時間的な対応
  • 歌唱者固有の声質や歌唱上の癖

これらは同じ種類の情報ではない。例えば、音高は主に基本周波数に関係する一方、音色はスペクトル包絡やフォルマントなどに関係する。

そのため、単一の数値だけで歌声を完全に表現することはできない。複数の特徴量と正確な教師ラベルを組み合わせる必要がある。

1.2 P3.4 の役割

P3.4 の名称は QC_Table_Markers である。

この版の中心的な役割は、音声特徴量の品質確認を支援する GUI において、QC（Quality Control：品質管理）の検出結果を表形式で見分けやすくすることである。

既知の P3.4 の変更点は、QC テーブルの判定マーカーと行の色分けである。

マーカー意味
×大きな F0（基本周波数）変化が検出された
○信頼度が低い可能性がある
●RMS が低い可能性がある
—F0 が未推定、または無声区間などの候補
✓対象の検査項目でフラグが検出されていない

これらのマーカーは、データを目視確認するための補助情報である。

マーカーが付いたことだけを理由に、音声が不良であると確定してはならない。

例えば、音高が急激に変化することは、歌唱のグリッサンドや音程移動でも起こり得る。RMS が低い区間は、無音、ブレス、語尾の減衰などを表している可能性もある。

QC は、確認が必要な箇所を効率よく探すための仕組みであり、人間による判定や正しいアノテーションを置き換えるものではない。

1.3 P3.4 の位置づけ

P3.4 は、歌声合成モデルそのものではない。

役割を大きく分けると、次のようになる。

  1. 音声を収録する。
  2. 音声から特徴量を抽出する。
  3. 特徴量を検査して問題候補を検出する。
  4. 問題候補を確認し、データの採否を判断する。
  5. 正確なラベルを整備する。
  6. 学習に適したデータセットを構築する。
  7. モデルを学習し、評価する。

P3.4 は、このうち主に 3 と 4 の作業を支援する品質確認ツールとして位置づける。

P3.4 の QC テーブルに表示されたデータが、そのまま学習に適していることを保証するものではない。

2.2 それぞれの工程の役割

音声収録

歌声または対象となる発声を WAV ファイルとして保存する。

収録時には、録音レベル、マイクの距離、部屋の反響、背景ノイズ、歌唱内容などが後続処理に影響する。

特徴量抽出

音声波形を数値的な特徴量へ変換する。

例えば、音高を推定した F0、音量の目安となる RMS、周波数成分を表すスペクトル特徴などがある。

QC 検査

特徴量の異常候補を検出する。

この工程で検出されるのは、あくまでルールに基づいた疑わしい箇所である。音楽的に正しいかどうかを完全に判断するものではない。

人間による確認

波形や特徴量のグラフ、実際の音声、歌詞、音素、MIDI などを照合する。

ここで、解析上の誤りと、実際の歌唱表現を区別する。

データセット構築

採用できる音声と正確なラベルを関連付け、学習用の入力と教師信号を整える。

モデル学習

検証済みのデータを用いて、目的に応じたモデルを学習する。

特徴量を抽出しただけでは、歌声を生成するモデルは完成しない。

3. P3.4 の QC テーブル

3.1 QC テーブルの目的

音声の特徴量を時系列で検査すると、確認が必要なフレームが多数見つかる場合がある。

すべてのフレームを一つずつグラフから探す方法では、確認作業が煩雑になる。

QC テーブルは、問題候補を一覧表示し、どの時刻に何の検査フラグが付いたのかを識別しやすくするための仕組みである。

例えば、次のような情報を表形式で確認する構成が考えられる。

  • 対象フレーム
  • 時刻
  • F0
  • 信頼度の目安
  • RMS
  • 検出されたフラグ
  • 確認結果

実際の P3.4 に表示される列名、列順、数値形式、ソート条件は、実装コードを確認して確定する必要がある。

3.2 マーカーの読み方

× — 大きな F0 変化

F0 は Fundamental Frequency（基本周波数）を意味する。

有声音では、基本周波数は声帯振動の繰り返しに対応する周波数として扱われる。F0 が高いほど、一般に知覚される音高も高くなる。

例えば、基本周波数が 200 Hz から 220 Hz に変化した場合、音高差はセント単位で次のように表せる。

[ \Delta c=1200\log_2\left(\frac{220}{200}\right) ]

約 165 セントの上昇に相当する。

大きな F0 変化の検出は、前後のフレーム間で音高が急激に変化した箇所を探すために利用できる。

ただし、F0 の急変には複数の原因がある。

  1. 実際の音程移動
  2. ビブラートやポルタメント
  3. F0 推定器が誤った周期を選択した
  4. 倍音を基本周波数と誤認した
  5. 有声音から無声音への遷移
  6. ノイズや極端に小さい音量の影響
  7. フレーム境界での推定不安定

したがって、× は「誤り確定」ではなく「確認候補」と解釈する。

○ — 低信頼度の候補

F0 推定などの処理には、推定値がどの程度信頼できるかを示す指標が設けられる場合がある。

P3.4 で扱われる信頼度は、元の特徴抽出器が出力する正式な確率であるとは限らない。プロジェクトの特徴量仕様では、f0_confidence_proxy のような代理指標が使われている。

proxy は「代理指標」を意味する。

つまり、信頼度を直接測定したものではなく、推定結果の妥当性を判断するために設計された参考値である可能性がある。

注意点は次のとおり。

  • 0.9 という値が、必ず 90% の正解率を意味するわけではない。
  • しきい値を変更すると、検出されるフレーム数が変わる可能性がある。
  • 音量、ノイズ、母音、声質によって指標の挙動が変化する場合がある。
  • 実際の F0 が正しいかどうかは、音声と他の情報を使って確認する必要がある。

● — 低 RMS の候補

RMS は Root Mean Square（平方平均平方根）であり、信号の振幅の大きさを示すために利用される。

離散信号 (x[n]) の RMS は、対象区間のサンプル数を (N) とすると、次の式で求められる。

[ \mathrm{RMS}=\sqrt{\frac{1}{N}\sum_{n=0}^{N-1}x[n]^2} ]

RMS が小さい場合、音声の振幅が小さいことを意味する。

ただし、低 RMS が必ず録音失敗を意味するわけではない。

例えば、次のような正常な区間でも RMS は低くなることがある。

  • 無音
  • ブレス
  • 語尾の減衰
  • 小さな声で歌う部分
  • 発声前後の遷移
  • 音楽的に意図された休符

そのため、RMS は単独でデータの採否を決める指標として使わない。

— — F0 未推定・無声区間などの候補

F0 が推定されないフレームは、必ずしも異常ではない。

例えば、次のような状況がある。

  • 無音
  • 息だけの音
  • 無声子音
  • 音量が小さく周期性が不明瞭な区間
  • ノイズが大きく周期を検出できない区間
  • 推定器が有声音と判断できなかった区間

また、歌声では、有声音と無声音が短い時間で交互に現れることもある。

F0 が存在しない区間に対して、無理に音高を補完すると、誤った教師データが生成される可能性がある。

無声区間の F0 を 0 として保存する実装もあれば、NaN や別のマスクで表現する実装もある。実際の保存形式は NPZ の配列仕様を確認すること。

✓ — 対象検査でフラグなし

✓ は、該当する検査項目においてフラグが検出されていないことを示す。

これは、音声全体が正しいことを保証するものではない。

例えば、次のような問題は、単純な F0・RMS 検査だけでは検出できない場合がある。

  • 歌詞と音声の不一致
  • 音素ラベルの誤り
  • MIDI と実際の歌唱の不一致
  • 音声のクリッピング
  • マイクや部屋の音響による色付け
  • 歌唱者の取り違え
  • データの重複
  • 音声ファイルとメタデータの対応ミス

✓ は「QC が完了し、すべて正しい」という意味ではなく、「この検査では問題候補が検出されなかった」と理解する。

3.3 行の色分け

P3.4 では、QC テーブルのマーカーに加えて、行の色分けによって確認対象を識別しやすくする変更が含まれる。

色は視認性を高める補助情報である。色だけに依存すると、表示環境や色覚の違いによって判断しにくくなる可能性がある。

マーカーと文字情報を併用することには、次の利点がある。

  • 色を識別しにくい場合にも状態を読み取れる。
  • 表をコピーした場合に記号を確認できる。
  • どの種類の問題が検出されたかを区別しやすい。

色とマーカーの厳密な対応関係は、実際の GUI 実装を確認して記録する。

4. 音声特徴量の基礎

この章では、RG Singing AI で扱われる主要な特徴量を、モデル開発との関係を含めて説明する。

4.1 音声波形

音声は、時間とともに変化する信号である。

デジタル音声では、一定の間隔で信号の振幅を記録する。

サンプリング周波数が 44,100 Hz の場合、1 秒間に 44,100 個のサンプルが記録される。

PCM 形式では、各サンプルが振幅値として保存される。

音声波形は元の信号を保持する重要なデータであり、後から別の特徴量を計算し直すための基礎となる。

可能な限り、元の WAV ファイルを保持し、特徴量だけを唯一の保存データにしないことを推奨する。

4.2 F0（基本周波数）

F0 は、有声音の周期性を分析して推定する主要な特徴量である。

歌声モデルでは、音高の軌跡を学習するために利用できる。

ただし、実際の音声に対する F0 推定には誤差がある。

特に注意すべきなのは、オクターブ誤りである。

例えば、実際の基本周波数が 150 Hz であるのに、推定器が 300 Hz を出力する場合がある。これは 2 倍の周波数であり、音高では 1 オクターブの差に相当する。

F0 の品質を確認するときは、次の情報を組み合わせることが望ましい。

  • F0 の時系列
  • F0 推定の信頼度に関する指標
  • RMS
  • スペクトル
  • 実際の音声
  • MIDI や正しい音高ラベル
  • 前後の音高変化

MIDI は意図された音符の情報を提供できるが、実際の歌唱音高が MIDI と完全に一致するとは限らない。

したがって、MIDI をそのまま実測 F0 の正解値として扱わないこと。

4.3 RMS（振幅の大きさ）

RMS は、音声の振幅を表すための指標である。

声の強弱を調べるための参考情報になるが、RMS は知覚される音量そのものではない。

マイクのゲイン、録音距離、部屋の音響、周波数特性なども RMS に影響する。

異なる録音セッション間で RMS を比較する場合には、録音条件の違いを考慮する必要がある。

4.4 Log-Mel Spectrogram

メルスペクトログラムは、時間・周波数の情報を二次元配列として表現する特徴量である。

一般的な処理では、次のような工程を経る。

  1. 音声を短いフレームに分割する。
  2. フレームごとに周波数成分を計算する。
  3. メル尺度に基づくフィルタバンクを適用する。
  4. エネルギーを計算する。
  5. 対数変換を適用する。

メル尺度は、人間の聴覚特性を参考にした周波数尺度である。

Log-Mel Spectrogram は、音色、音素、音声の時間的な変化などをモデルに入力する際に有用である。

ただし、Log-Mel だけで歌詞や音素が必ず正確に復元できるわけではない。

また、フレーム長、ホップ長、メルフィルタ数、正規化方法、対数変換の下限値などによって特徴量の数値は変わる。

学習時と推論時に異なる設定を使うと、モデルに入力されるデータの分布が変わるため、設定を固定・記録する必要がある。

4.5 スペクトル包絡

スペクトル包絡は、音声の周波数スペクトルにおける大まかな形状を表す特徴である。

声帯振動などによる励振成分と、声道の共鳴による音色の変化を区別するうえで重要になる。

同じ音高でも、母音や発声方法が異なるとスペクトルの形状は変わる。

スペクトル包絡は、声質や母音の音色を表現するための情報として利用できる。

ただし、抽出方法によって得られる包絡の意味や精度は異なる。

4.6 フォルマント

フォルマントは、声道の共鳴に関連するスペクトル上の特徴である。

母音の識別や音色の分析に関係する。

F1、F2、F3 などのフォルマント周波数を推定する方法があるが、実際の歌声では、次の要因によって推定が難しくなる場合がある。

  • 高い音高
  • 強いビブラート
  • 息の混ざった発声
  • ノイズ
  • フォルマントの重なり
  • 音量の低さ
  • 音素の遷移

推定値を無条件に正解データとして扱わず、必要に応じて音声やスペクトルを確認すること。

4.7 HNR

HNR は Harmonics-to-Noise Ratio（調波対雑音比）である。

周期的な調波成分と、非周期的な成分の比率を評価するために利用される。

HNR が高い場合、周期的な成分が相対的に強いことを示す場合がある。

ただし、HNR は声質の良し悪しを直接評価する指標ではない。

歌声には、息の混ざった発声、声帯振動の不規則性、子音、ノイズ成分などが含まれる。

HNR の低さだけで音声を不良と判断すると、学習に必要な声質の多様性を失う可能性がある。

また、プロジェクトの特徴量に hnr_db_proxy のような名前が使われている場合、正式な HNR 推定値ではなく代理指標である可能性を考慮する必要がある。

4.8 非周期性・息声・声質

声帯振動の周期性、非周期的な成分、息の混ざり方などは、声質を分析するための手掛かりになる。

ただし、「息声」や「柔らかい声」といった主観的な特徴を、数値だけで完全に表現することは難しい。

モデルで扱う場合は、音響特徴量だけでなく、目的に応じたラベルや学習方法を検討する必要がある。

5. フレームと時間軸

5.1 フレームとは何か

音声を分析するとき、通常は音声全体を一度に処理するのではなく、短い時間区間に分割して特徴量を計算する。

この短い区間をフレームと呼ぶ。

例えば、あるフレームの時刻が 1.25 秒であれば、その付近の音声を使って F0 や RMS などを計算する。

フレームごとに特徴量を保存することで、音高や音量の時間的な変化を分析できる。

5.2 ホップ長とフレーム数

隣り合うフレームをどれだけ離して計算するかをホップ長と呼ぶ。

ホップ長を短くすると、時間方向の変化を細かく追跡しやすくなる。一方、計算量や保存量が増える。

ホップ長を長くすると計算量を減らせるが、短い子音や急激な変化を捉えにくくなる場合がある。

実際のフレーム時刻は、特徴抽出器が定義する規則に従う。

次の情報を、特徴量と一緒に管理することを推奨する。

  • サンプリング周波数
  • フレーム長
  • ホップ長
  • 窓関数
  • FFT サイズ
  • フレーム中心を時刻として扱うかどうか
  • パディング方法
  • 特徴量の単位
  • 特徴量の保存形式

5.3 時刻の一致

複数の特徴量を組み合わせるには、各配列の時刻対応が正しいことが重要である。

例えば、F0 の 100 番目の値と Log-Mel の 100 番目のフレームが、同じ時間区間を表しているとは限らない。特徴抽出の設定が異なれば、配列長や時間対応が異なる可能性がある。

学習時には、単純に配列のインデックスだけを合わせるのではなく、フレーム時刻と抽出設定を確認する必要がある。

6. 特徴量 NPZ とファイル管理

6.1 NPZ とは

NPZ は、NumPy の配列を複数まとめて保存するファイル形式である。

例えば、次のような特徴量を一つのファイルに保存できる。

  • frame_times_sec
  • frame_rms
  • log_mel
  • f0_hz
  • f0_confidence_proxy
  • spectral_envelope
  • hnr_db_proxy
  • formants_hz_estimate

上記はプロジェクトで確認されている特徴量名の例であり、すべてのファイルに必ず存在することを保証する一覧ではない。

6.2 NPZ の利点

  • 複数の数値配列を一つのファイルにまとめられる。
  • NumPy から扱いやすい。
  • 音声を繰り返し解析するコストを減らせる。
  • 学習用の前処理データとして利用できる。
  • 配列形状や数値型を確認できる。

6.3 NPZ の注意点

NPZ は、配列の意味や単位を自動的に説明してくれる形式ではない。

例えば、f0_hz が Hz 単位なのか、正規化済みの値なのかを、ファイル名だけで完全に判断することはできない。

特徴量ごとに次の情報を仕様書として管理することを推奨する。

項目内容
名前配列のキー
意味何を表す値か
単位Hz、秒、dB など
形状1 次元、2 次元など
データ型float32、float64 など
時間対応フレーム時刻との対応
欠損値0、NaN、別のマスクなど
抽出方法使用したアルゴリズム
設定フレーム長、ホップ長など
バージョン抽出器のバージョン

学習時に異なる設定で抽出した特徴量を混在させると、モデルが意図しない差を学習する可能性がある。

6.4 元の音声を保持する

特徴量 NPZ は元の音声の完全な代替ではない。

元の WAV を保持しておけば、後から次のような処理が可能になる。

  • 新しい F0 推定器による再解析
  • 特徴抽出設定の変更
  • 新しい特徴量の追加
  • 誤った特徴量の再生成
  • 音声と特徴量の再照合

特徴量だけを残して WAV を削除すると、再解析できる範囲が大幅に制限される。

7. 関連データセットの仕様

7.1 基本的な音声形式

関連する RG Singing AI データセット仕様では、次の形式が基準として示されている。

  • サンプリング周波数: 44,100 Hz
  • チャンネル数: モノラル 1 チャンネル
  • 音声形式: PCM 24-bit WAV

これらはデータセット側の基準である。P3.4 の個々の解析処理がすべて同じ条件を要求するかどうかは、各スクリプトの実装に従う。

7.2 データセットのディレクトリ構成

関連するデータセット仕様では、次の構成が使われている。

RG_SingingAI_Dataset/
├─ raw/
│  └─ audio/
│     └─ S001_010001.wav
├─ metadata/
│  └─ S001_010001.json
├─ reference/
│  ├─ midi/
│  └─ lyrics/
├─ annotations/
│  ├─ note/
│  └─ alignment/
├─ qc/
├─ splits/
└─ training_npz/

この図は主要な役割を理解するための例である。実際のフォルダ名やファイル配置は、導入している版の README、スクリプト、設定に従う。

raw/audio/

元の録音 WAV を保存する。

metadata/

録音日時、話者 ID、セッション ID、テイク ID、音声ファイルの情報、ハッシュなどを管理する。

reference/midi/

参照用 MIDI を保存する。

MIDI は、音符、音高、ベロシティ、タイミングなどの情報を持つ。

ただし、MIDI のノート開始時刻は、必ずしも実際の歌唱における発声開始時刻と一致しない。

参照用の歌詞ファイルを保存する。

歌詞の内容と実際に録音された音声が一致することを確認する必要がある。

annotations/note/

MIDI などに基づくノートイベントの参照情報を保存する。

ノートイベントの参照情報は、音声中の正確な音素境界を意味しない。

annotations/alignment/

音声と歌詞・音素などの時間対応を扱うための領域である。

正しいアラインメントが存在しない場合は、未検証のタイミングを正解として扱わない。

qc/

QC の結果を機械可読な形式で管理するための領域である。

splits/

学習・検証・テスト用の分割情報を保存するための領域である。

training_npz/

特徴量抽出や学習準備で生成された NPZ などを保存する領域として利用できる。

実際の保存先は、使用するスクリプトの引数と設定を確認すること。

7.3 メタデータと SHA-256

関連する録音ツールでは、音声ファイルの SHA-256 ハッシュをメタデータに保存する仕様が確認されている。

SHA-256 は、ファイル内容から計算されるハッシュ値である。

同じファイル内容であれば、通常は同じハッシュ値になる。ファイルの内容が変わると、ハッシュ値も変わる可能性が極めて高い。

SHA-256 は次の用途に有用である。

  • ファイルが変更されていないかの確認
  • データの取り違えを検出する補助
  • 処理前後のファイル整合性確認
  • データセットの監査

ただし、SHA-256 は音声内容の正しさを保証しない。

誤った歌詞ラベルが付いた音声でも、そのファイルの SHA-256 は正常に計算できる。

ファイルの完全性と、学習データとしての正確性は別々に検証する。

8. P3.4 の使用方法

この章では、P3.4 の既知の目的に沿って、一般的な QC 作業手順を整理する。

実際のボタン名、起動方法、引数、入力ファイルの選択方法は、P3.4 の同梱 README と GUI 実装を確認してから確定する。

8.1 起動前の準備

  1. P3.4 の ZIP を展開する。
  2. 展開先の README を読む。
  3. 使用する Python のバージョンを確認する。
  4. 必要なライブラリが導入されているか確認する。
  5. 対象の WAV と特徴量 NPZ の場所を確認する。
  6. 元データをバックアップする。

プロジェクトの関連ツールでは、Python 仮想環境を使用する構成が採用されている。

仮想環境を利用すると、プロジェクトごとのライブラリを分離できるため、他の Python プロジェクトとの依存関係の衝突を減らせる。

P3.4 の実際の起動スクリプト名は、同梱ファイルに基づいて確認すること。別バージョンの起動コマンドをそのまま使用しない。

8.2 対象データの選択

解析対象の WAV と NPZ が正しく対応していることを確認する。

ファイル名が似ているだけでは、同一の録音から生成されたことを保証できない。

確認する項目は次のとおり。

  • WAV のファイル名
  • NPZ のファイル名
  • 話者 ID
  • セッション ID
  • テイク ID
  • 音声の長さ
  • サンプリング周波数
  • 特徴量の配列長
  • フレーム時刻
  • 対応するメタデータ

8.3 QC テーブルの確認

テーブルに表示されたマーカーを見て、確認が必要な箇所を探す。

推奨する確認順序は次のとおり。

  1. × が付いた F0 の急変箇所を確認する。
  2. ○ が付いた低信頼度候補を確認する。
  3. ● が付いた低 RMS 候補を確認する。
  4. — が付いた未推定・無声候補を確認する。
  5. フラグが付いていない区間も、必要に応じてサンプリング確認する。

マーカーの有無だけで最終判断を行わず、グラフ、音声、歌詞、MIDI などを照合する。

8.4 F0 の急変を確認する手順

  1. 急変の前後の時刻を確認する。
  2. F0 の値と変化量を確認する。
  3. RMS が極端に小さくないか確認する。
  4. 信頼度の目安を確認する。
  5. 実際の音声を再生する。
  6. MIDI や正しい音高ラベルと照合する。
  7. 実際の歌唱表現か推定誤りかを判断する。

歌唱表現として正しい場合は、異常として除外する必要はない。

推定誤りの場合は、F0 の再推定、区間の除外、ラベル修正など、目的に応じた対応を検討する。

8.5 低 RMS 区間を確認する手順

  1. 該当区間の時刻を確認する。
  2. 音声を再生する。
  3. 無音、ブレス、語尾、弱い発声、録音不良のどれに近いかを判断する。
  4. 学習目的に応じて採用可否を決める。

無音やブレスが正常な歌唱データに含まれる場合、それらを一律に削除すると、自然な歌唱のタイミングや音の減衰を学習できなくなる可能性がある。

8.6 未推定 F0 区間を確認する手順

  1. 該当時刻を確認する。
  2. 音声を再生する。
  3. 無声音、息、無音、低信頼度の有声音などを区別する。
  4. 目的に応じて F0 の欠損表現を維持するか、再解析するかを決める。

F0 が存在しない区間に、前後の値を機械的にコピーする処理は避ける。

補間を採用する場合も、補間値と実測値を区別して管理する。

8.7 QC 結果の記録

品質管理では、問題を検出しただけでは不十分である。

最終的な判断と、その理由を記録することが望ましい。

例えば、次のような情報を管理する。

  • 対象ファイル
  • 対象時刻
  • 検出されたフラグ
  • 人間による判定
  • 判定理由
  • 再解析の有無
  • 再録音の有無
  • 判定者
  • 判定日時
  • 使用した特徴抽出器のバージョン

これらは今後の監査、再解析、データセット改善に役立つ。

ただし、P3.4 に上記のすべての記録機能が実装されていると断定するものではない。既存 GUI にない項目は、別途の管理方式として導入を検討する。

9. データ品質の判定基準

9.1 自動 QC と人間の判定を分離する

品質管理では、次の 3 つを別の概念として扱う。

  1. 自動検査が検出したフラグ
  2. 人間が確認した結果
  3. 学習データとしての採否

例えば、F0 の急変フラグが検出されても、人間が確認した結果、実際の音程移動であれば採用可能な場合がある。

反対に、フラグが検出されていなくても、歌詞ラベルが間違っていれば学習データとして採用できない場合がある。

9.2 推奨する判定状態

将来的なデータ管理では、次のような状態を区別するとよい。

状態意味
pending_review未確認
accepted確認済みで採用可能
needs_reanalysis特徴量の再解析が必要
needs_rerecording再録音が必要
hold判断保留
rejected採用不可
annotation_required音声とラベルの確認・修正が必要

これらは今後の管理方式としての提案であり、P3.4 にすべての状態が実装されているという意味ではない。

状態を導入する場合は、名称、遷移条件、必要な記録項目を仕様として固定すること。

9.3 再解析と再録音の違い

再解析が適切なケース

  • F0 推定が不安定
  • 特徴抽出設定に誤りがある
  • 特徴量ファイルが破損している
  • 新しい抽出器で品質を改善できる可能性がある
  • 元の WAV は問題なく保持されている

再録音が適切なケース

  • 音声が極端にクリッピングしている
  • 必要な発声が録音されていない
  • 背景ノイズが大きい
  • マイク入力が切れている
  • 対象となる歌唱が間違っている
  • 音声が欠落している

再解析では、元の WAV に含まれない情報を復元できない。

録音そのものに問題がある場合は、再解析だけで解決しようとしない。

9.4 採用と保留の違い

保留は、採用不可と同義ではない。

例えば、F0 の推定が不安定でも、実際の音声や正しいラベルを確認するための情報が不足しているだけなら、保留して追加確認することが適切である。

判断が確定していないデータを、無理に採用・不採用のどちらかに分類しないこと。

10. 学習データとして採用するための条件

10.1 音声が存在するだけでは不十分

モデル学習では、入力と教師信号の対応が重要である。

例えば、音声に対して「あ」というラベルを付ける場合、その時間区間で実際に「あ」と発声されていることを確認する必要がある。

音声が存在していても、音素の境界や歌詞が誤っていれば、モデルは誤った対応を学習する可能性がある。

10.2 MIDI と音声の時間対応

MIDI には音符の開始時刻と終了時刻が含まれるが、実際の歌唱では、次の要因によって音声の時間位置が変わる。

  • 発声の立ち上がり
  • 子音の持続時間
  • ブレス
  • 歌唱者のタイミングの揺れ
  • レガート
  • ポルタメント
  • 音符間の移行
  • 録音開始時刻のずれ

したがって、MIDI ノートの開始・終了時刻を、そのまま音素境界として扱ってはならない。

正確な時間対応が必要なタスクでは、音声を参照してアラインメントを検証する必要がある。

10.3 音素ラベルの検証

学習データには、必要に応じて次のような情報を含める。

  • 音素ラベル
  • 音素の開始時刻
  • 音素の終了時刻
  • 対応する歌詞
  • 対応する音符
  • 話者 ID
  • セッション ID
  • 元音声への参照
  • アノテーションの検証状態

ただし、すべてのモデルで同じ教師ラベルが必要なわけではない。

モデルの目的を決めたうえで、必要なラベルを定義すること。

10.4 学習用・検証用・テスト用データの分割

関連するデータセット処理では、group_id、phrase_id、song_id、source_group_id などのグループ情報を用いてデータを分割する設計がある。

これはデータリークを防ぐために重要である。

例えば、同じフレーズの別テイクが学習用とテスト用に分かれていると、モデルが未知の歌唱をどの程度扱えるかを正しく評価できない可能性がある。

分割する際は、タスクに応じて同じ曲・同じフレーズ・同じ録音元などが複数の分割にまたがらないようにする。

どの単位で分割するべきかは、モデルの評価目的に合わせて決める。

11. 既知の解析事例と注意点

11.1 解析対象の例

過去に確認された音声ファイルの例は、次のとおりである。

S001_010001.wav

記録された概要は以下のとおり。

  • モノラル
  • サンプリング周波数 44,100 Hz
  • サンプル数 218,112
  • 長さ約 4.946 秒

この音声について、過去の確認ではハミングのみの録音と説明されている。

また、アノテーションには a と i の音素ラベル、MIDI ノート 60 と 64 が含まれていた。

ハミング音声に対して母音の音素ラベルを付けている場合、その対応が実際の発声と一致するか確認する必要がある。

ハミング中に口の形や発声方法が変わることはあるが、それだけで通常の母音を発声していると断定できるわけではない。

この音声を教師データに使う場合は、録音内容、音素ラベル、MIDI の対応を再確認すること。

11.2 特徴量の例

過去の解析では、次のような特徴量が確認されている。

  • frame_times_sec
  • frame_rms
  • log_mel
  • f0_hz
  • f0_confidence_proxy
  • spectral_envelope
  • hnr_db_proxy
  • formants_hz_estimate

また、F0 については 845 フレーム中 610 フレームで正の値が記録され、推定された有声音の F0 の中央値は約 173.09 Hz と報告されている。

ただし、これらは過去に解析された特定のファイルの結果であり、P3.4 全体の性能評価ではない。

11.3 F0 の疑わしい急変

過去の解析では、約 4.760 秒付近で F0 が約 991.011 Hz、信頼度の代理指標が約 0.381538、RMS が約 0.0001382 となったフレームが報告されている。

直前フレームとの音高差は約 3,250.96 セントとされ、急激な変化の候補になっている。

この値は、F0 推定誤りの可能性を調べるうえで重要な候補である。

しかし、数値だけで誤りと確定することはできない。

確認手順は次のとおり。

  1. 該当時刻の音声を再生する。
  2. 前後の波形を確認する。
  3. F0 の推移を確認する。
  4. 信頼度の代理指標を確認する。
  5. RMS を確認する。
  6. スペクトルと倍音構造を確認する。
  7. 実際の音高と推定結果を照合する。

このような疑わしいフレームは、モデル学習に使う前に確認する。

11.4 過去の NPZ に関する注意

過去のデータセット生成結果では、Log-Mel 配列が (845, 80)、ラベル付きフレームが 138、ラベル ID が 0 のフレームが 707 と報告されている。

また、状態は reviewed_annotation_required とされていた。

この結果からは、少なくとも当該データについて、アノテーションの確認が必要だったことが分かる。

ただし、ラベル ID 0 が具体的に何を意味するかは、ラベル定義やデータセット生成コードを確認しなければ断定できない。

0 が無音、未ラベル、未知クラス、パディングなどのどれを意味するかによって、データの扱いは変わる。

したがって、ラベル ID 0 を一律に学習対象から除外する、あるいは有効な教師ラベルとして扱うといった判断は、仕様を確認してから行う。

11.5 学習への利用判断

上記の例は、特徴量が抽出できていても、学習用データとしての妥当性は別途確認しなければならないことを示している。

当該音声を学習に使う場合は、次の条件を確認する。

  • 音声内容が記録されているラベルと一致する。
  • F0 の疑わしい箇所が確認されている。
  • 音素と音声の対応が妥当である。
  • MIDI と実際の歌唱の時間対応が整理されている。
  • 特徴量の欠損値や異常値の扱いが定義されている。
  • 学習に必要なラベルがそろっている。
  • ファイルとメタデータの対応が正しい。

これらを確認するまでは、当該データを学習用データとして確定しないことを推奨する。

12. 技術的な制約と誤解しやすい点

12.1 QC は自動診断器ではない

QC が検出するのは、設計されたルールに合致する問題候補である。

音楽的な正しさ、歌詞の正しさ、歌唱表現の自然さを完全に判断するものではない。

12.2 代理指標は正解確率ではない

f0_confidence_proxy や hnr_db_proxy のように proxy が付いた値は、正式な確率や測定値と同一視しない。

値の意味、算出方法、しきい値を理解したうえで使用する。

12.3 F0 が未推定でも音声は正常な場合がある

無声音やブレスには、通常の有声音と同じ意味での F0 が存在しない場合がある。

F0 がないことだけを理由に、音声を削除しない。

12.4 RMS が小さくても正常な場合がある

音量が小さい区間は、歌唱表現や発声上の理由で存在する。

低 RMS のフレームは、実際の音声を確認してから判断する。

12.5 MIDI は実測音声の代わりにならない

MIDI は参照情報である。

実際の歌唱の音高、タイミング、音素境界を完全に表すものではない。

12.6 特徴量抽出の成功は学習の成功を意味しない

特徴量が正常に保存されても、データの意味やラベルが正しいとは限らない。

学習前には、特徴量の形状、単位、時間対応、欠損値、教師ラベルを検証する。

12.7 ✓ は完全な品質保証ではない

マーカーは、対象の検査でフラグが付かなかったことを表す。

検査対象外の問題が存在する可能性は残る。

13. 安全性とデータ保護

13.1 ローカル処理について

関連する録音ツールの README では、外部 API やテレメトリを実装していない旨が説明されている。

ただし、これは関連する録音ツールについての記載であり、P3.4 のすべての依存ライブラリやすべての処理について、独立した通信監査が完了したことを意味しない。

外部送信の有無を厳密に確認したい場合は、次の方法を採用する。

  1. ソースコードで HTTP クライアントやソケット処理を検索する。
  2. 依存ライブラリを確認する。
  3. 起動時と解析時の通信を監視する。
  4. 必要に応じてファイアウォールで外向き通信を制限する。
  5. 検証結果を記録する。

13.2 元データを保護する

QC や特徴量抽出の試験を行う前に、元の WAV とアノテーションをバックアップする。

解析結果を変更する場合は、元ファイルを直接上書きするのではなく、別ファイルとして保存する方法を推奨する。

13.3 データの追跡可能性

次の情報を管理すると、後からデータの由来を追跡しやすくなる。

  • 元 WAV の SHA-256
  • 特徴量抽出器のバージョン
  • 使用した設定
  • アノテーションのバージョン
  • QC の結果
  • 人間による判定
  • 処理日時
  • 学習データセットのバージョン

14. P3.4 の検証チェックリスト

P3.4 を正式なデータ管理工程に組み込む前に、次の項目を確認する。

14.1 起動・基本動作

  • 正しい P3.4 のフォルダから起動できる。
  • 必要な Python ライブラリが導入されている。
  • 対象の NPZ を読み込める。
  • 必須の配列が存在しない場合、適切なエラーが表示される。
  • 空の配列や欠損値がある場合の挙動を確認した。
  • 不正なファイルを読み込んでも、元データが破損しない。

14.2 QC テーブル

  • × の意味が表示または説明されている。
  • ○ の意味が表示または説明されている。
  • ● の意味が表示または説明されている。
  • — の意味が表示または説明されている。
  • ✓ の意味が表示または説明されている。
  • 複数のフラグが同時に発生した場合の表示を確認した。
  • 行の色分けとマーカーの対応を確認した。
  • テーブルの時刻とグラフの時刻が一致している。
  • 未推定 F0 と無声区間の扱いを確認した。

14.3 数値と時間軸

  • F0 の単位が Hz であることを確認した。
  • RMS の計算方法と単位を確認した。
  • 信頼度の代理指標の意味を確認した。
  • フレーム時刻の定義を確認した。
  • 配列長とフレーム時刻の対応を確認した。
  • NaN、Inf、0 などの値の扱いを確認した。
  • F0 の急変検出に使うしきい値を確認した。
  • 低 RMS の検出に使うしきい値を確認した。

14.4 データ保護

  • 元 WAV が変更されないことを確認した。
  • 元 NPZ が変更されないことを確認した。
  • QC の出力先を確認した。
  • 解析結果の上書き動作を確認した。
  • バックアップを取得した。
  • 外部通信の要否と有無を確認した。

15. 今後の改善方針

以下は、P3.4 の既存機能と区別した今後の開発提案である。

15.1 優先度 A：判定作業の記録

QC の検出結果だけでなく、人間による判定を永続化する仕組みを整備する。

記録する情報の候補は次のとおり。

  • 対象ファイル
  • 対象区間
  • QC フラグ
  • 判定状態
  • 判定理由
  • 判定者
  • 判定日時
  • 再解析の有無
  • 再録音の有無

判定記録は、元の特徴量とは分離して管理する。

これにより、QC のしきい値を変更した場合でも、以前の人間による判断を追跡できる。

15.2 優先度 A：音声の再生と該当区間への移動

QC テーブルで選択した行の時刻に対応する音声を再生できるようにする。

例えば、1.25 秒付近にフラグが付いている場合、その周辺だけを再生する。

この機能により、グラフ上の異常候補と実際の音声を照合しやすくなる。

再生機能を追加する場合は、次の点を確認する。

  • 元の WAV と特徴量の対応
  • サンプリング周波数
  • 再生区間の境界
  • 音声が短い場合の処理
  • 無効な開始・終了時刻の処理
  • 再生中に別の区間を選択した場合の挙動

15.3 優先度 A：レポート出力

QC の結果を、後から確認できる形式で出力する。

候補となる形式は次のとおり。

  • JSON：機械処理向け
  • CSV：表計算ソフト向け
  • HTML：人間による閲覧向け
  • Markdown：技術報告書向け

レポートには、対象ファイル、解析設定、検出フラグ、時刻、特徴量の要約、判定結果などを含めることが望ましい。

レポートを出力するだけでなく、どの元データから生成されたかを追跡できるようにする。

15.4 優先度 A：アノテーション検証

歌詞・音素・音符と音声の時間対応を確認する仕組みを整備する。

特に、次の項目を区別する。

  • MIDI ノートイベント
  • 実際の音高
  • 歌詞
  • 音素
  • 音素の開始・終了時刻
  • 無声区間
  • ブレス
  • 未確認区間

未確認のアノテーションを、検証済みの正解ラベルと同じ扱いにしない。

15.5 優先度 B：QC の検出精度評価

しきい値を変更した場合に、検出結果がどのように変化するかを評価する。

人間が確認したデータを使って、次の項目を計測する。

  • 真陽性
  • 偽陽性
  • 真陰性
  • 偽陰性
  • 適合率
  • 再現率

例えば、F0 の急変検出で偽陽性が多すぎる場合、正しいビブラートや音程移動まで大量に検出している可能性がある。

一方、再現率が低い場合、実際の推定誤りを見逃している可能性がある。

単にフラグ数を減らすのではなく、人間が確認した正解データを使ってしきい値を評価する。

15.6 優先度 B：特徴量の再現性

同じ WAV と同じ設定から、同等の特徴量を再生成できることを確認する。

そのために、次の情報を保存する。

  • 特徴抽出器のバージョン
  • Python と主要ライブラリのバージョン
  • 特徴抽出設定
  • 元 WAV のハッシュ
  • 出力配列の形状
  • 生成日時

アルゴリズムやライブラリの変更によって特徴量が変化した場合は、その差を評価する。

15.7 優先度 B：異常検出の拡張

将来的には、F0 と RMS だけでなく、複数の特徴量を組み合わせた検査を検討する。

候補は次のとおり。

  • クリッピング検出
  • DC オフセット検出
  • 不自然な長時間無音の検出
  • 急激なスペクトル変化の検出
  • 音声の途中欠落の検出
  • チャンネル数やサンプリング周波数の不一致
  • ファイルとメタデータの不一致
  • 重複音声の検出
  • アノテーション範囲外の検出

ただし、無音、ブレス、音量の小さい発声を一律に異常と扱わないこと。

15.8 優先度 C：データセット管理との統合

QC の結果とメタデータを連携し、採用可能なデータだけを学習用データセットへ送る仕組みを検討する。

自動採用を行う場合は、条件を明文化する。

例えば、次の条件を独立して確認する。

  • 音声ファイルの完全性
  • メタデータの妥当性
  • 必須ラベルの存在
  • アノテーションの検証状態
  • QC の確認状態
  • グループ ID の存在
  • 学習対象タスクとの適合性

QC フラグがないという条件だけで自動採用しない。

16. モデル化・学習に進むための計画

16.1 まずモデルの目的を定義する

歌声 AI は、実現したい機能によって必要なモデル構造と教師データが異なる。

例えば、次のようなタスクが考えられる。

  1. 音声から F0 を推定する。
  2. 音声から音素を推定する。
  3. 音声から声質特徴量を推定する。
  4. MIDI と歌詞から歌声を生成する。
  5. 参照歌手の特徴を条件として歌声を生成する。
  6. 歌唱表現を学習して、音高・音量・音色の時間変化を生成する。

これらは別々のタスクであり、同じデータセットを無条件にそのまま利用できるわけではない。

最終目標が歌声生成であっても、最初から大規模な生成モデルを学習する必要はない。先に特徴抽出、ラベル検証、時間対応、データ分割を確立することが重要である。

16.2 推奨する段階的な開発

Phase A：データ検証

  • WAV の形式を検証する。
  • NPZ の配列を検証する。
  • メタデータを検証する。
  • アノテーションの整合性を検証する。
  • QC の結果を確認する。

Phase B：ベースラインモデル

目的を限定した小規模なモデルを用意する。

例えば、音声特徴量から音素ラベルを推定するなど、評価しやすいタスクを選ぶ。

Phase C：評価基盤

学習データとは独立した検証用・テスト用データを用意する。

評価指標を決め、モデルの性能を測定する。

Phase D：歌声生成モデル

教師データの正確性と評価基盤が整ってから、歌声生成モデルの設計・学習に進む。

この段階では、音響モデル、ボコーダー、条件付け方式などを検討する必要がある。

17. モデル学習時の重大な注意点

17.1 小規模データでの過学習

録音データが少ない場合、モデルが学習データの特徴を記憶してしまい、未知の歌唱に対応できなくなる可能性がある。

学習損失が下がることだけで、モデルが優秀になったと判断しない。

17.2 データリーク

同じ歌唱の別テイクや同じフレーズの断片が、学習用とテスト用に分かれていると、テスト結果が実際より良く見える場合がある。

分割は、曲・フレーズ・録音元などの関係を考慮して設計する。

17.3 ラベルの誤り

モデルは、与えられた教師ラベルを正しいものとして学習する。

誤った音素ラベルやタイミングが大量に含まれていると、モデルの性能が制限される。

学習前のラベル検証は、モデル構造の改善と同じくらい重要である。

17.4 特徴量の分布

異なるマイク、録音距離、音量、部屋の音響で収録された音声は、特徴量の分布が変わる可能性がある。

モデルが歌唱者の特徴ではなく、録音環境の違いを学習してしまう可能性を考慮する。

17.5 F0 の異常値

F0 の推定誤りをそのまま教師信号にすると、モデルが誤った音高変化を学習する可能性がある。

ただし、すべての急変を除去すると、正しい歌唱表現まで失われる。

異常候補を検出し、音声を確認してから扱いを決めること。

19. 総括

RG Singing AI Recording Tool v1.3.1 P3.4 QC Table Markers は、音声特徴量の品質確認において、問題候補を表形式のマーカーで識別しやすくする版である。

×、○、●、—、✓ は、確認対象を整理するための補助情報として扱う。

この版をデータ収録・特徴抽出工程に組み込む際には、次の原則を守ることが重要である。

  1. 自動 QC のフラグと人間による判定を分ける。
  2. F0 や RMS の異常候補だけで音声の採否を決めない。
  3. MIDI のタイミングを実際の音声の境界と同一視しない。
  4. 特徴量の形状、単位、時間対応を管理する。
  5. 元の WAV とメタデータを保持する。
  6. アノテーションが正しいことを確認してから学習に使う。
  7. 学習・検証・テストのデータリークを防ぐ。
  8. 解析設定とソフトウェアのバージョンを記録する。
  9. 未確認のデータを、検証済みの教師データとして扱わない。
  10. モデルの性能を、独立したデータと明確な評価指標で検証する。

最も重要なのは、特徴量の抽出精度だけでなく、音声・ラベル・時間対応の正確性を含めてデータセットの品質を管理することである。

QC テーブルは、その品質管理を支援するための一部である。モデルの品質を高めるには、正確な録音、正しいアノテーション、再現可能な特徴抽出、適切なデータ分割、そして独立した評価を一貫した工程として整備する必要がある。
